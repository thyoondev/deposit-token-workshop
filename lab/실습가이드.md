# 수강생 실습 가이드

[시작 안내](../README.md)의 예제를 실행해 잔액 80개를 확인했다면 여기서부터 진행합니다. 아래 명령은 모두 저장소 안의 `lab` 폴더에서 실행하세요.

제공 자료는 완성 코드입니다. 먼저 읽고 실행한 다음, 강사의 안내에 따라 일부를 수정합니다. 모든 파일을 지우고 처음부터 작성할 필요는 없습니다. 파일은 사용 중인 코드 편집기로 여세요.

## 실습 1 · 100개 발행하고 20개 소각하기

**목표:** 누가 토큰을 만들고, 고객은 어떤 승인을 하는지 확인합니다.

1. `scripts/demo.ts`를 엽니다.
2. `mint`가 있는 줄을 찾습니다. 운영자인 `bank`가 고객 `alice`에게 토큰 100개를 발행합니다.
3. `approve`가 있는 줄을 찾습니다. 고객이 `bank`에 토큰 20개를 사용할 권한을 줍니다.
4. `burn`이 있는 줄을 찾습니다. 운영자가 그 승인 범위 안에서 20개를 소각합니다.

```bash
npm run demo
```

잔액과 전체 토큰 수량이 모두 80개인지 확인하세요. `bank`와 `alice`는 프로그램이 준비한 연습용 계정입니다. 직접 지갑을 만들 필요는 없습니다. 이 예제의 소각은 토큰 수량을 줄이는 동작이며 실제 은행 계좌로 돈을 입금하지 않습니다.

**직접 바꿔보기:** 같은 파일의 `approve`와 `burn`에 있는 `u("20")`를 **둘 다** `u("30")`으로 바꾸고 저장합니다. 다시 실행하면 `After mint: 100.0`, `After burn: 70.0`, `Supply: 70.0`이 나와야 합니다. `u(...)`는 화면에 표시할 수량을 코드가 사용하는 정수 단위로 바꾸는 함수입니다.

확인한 뒤 두 값을 모두 `u("20")`으로 되돌리고 저장하세요. 이 데모는 실행할 때마다 새 연습 환경을 만들므로 앞선 실행의 잔액이 누적되지 않습니다.

## 실습 2 · 승인된 고객만 거래하기

**목표:** 고객 승인을 취소하면 거래가 거절되는지 확인합니다.

`contracts/KYCRegistry.sol`은 주소별 거래 자격을 저장합니다. `setVerified`는 상태를 바꾸고, `isVerified`는 현재 상태를 조회합니다. 승인 상태는 `true`, 미승인 상태는 `false`입니다. 실제 신분증을 수집하는 기능은 아닙니다.

```bash
npx hardhat test mocha --grep KYCRegistry
```

`5 passing`이 나오면 승인·취소·권한 없는 변경을 검사하는 항목이 모두 통과한 것입니다. 이어서 전송 관련 테스트를 실행합니다.

```bash
npx hardhat test mocha --grep "moves balances|transfer|spender"
```

`6 passing`을 확인한 뒤 `test/DepositToken.ts`에서 `rejects a transfer after`를 검색하세요. 고객 승인을 취소한 뒤 전송이 거절되는 과정을 볼 수 있습니다. `spender`는 고객 대신 전송을 실행하는 계정입니다. 이 실습에서는 대신 보내는 사람의 거래 자격도 확인합니다.

**확인 질문:** 보낼 토큰이 충분해도 거래가 거절되는 경우는 무엇인가요? 테스트 하나를 골라 거절 이유를 적어보세요.

## 실습 3 · 거래 중단과 특정 계정 동결

**목표:** 전체 거래를 멈추는 기능과 특정 계정만 제한하는 기능을 구분합니다.

`contracts/DepositToken.sol`에서 아래 함수를 찾습니다.

| 함수 | 하는 일 |
|---|---|
| `pause()` | 토큰 발행·소각·전송을 전체 중단 |
| `unpause()` | 전체 중단 해제 |
| `setFrozen(주소, true)` | 해당 계정 동결 |
| `setFrozen(주소, false)` | 해당 계정 동결 해제 |

```bash
npx hardhat test mocha --grep "pause|freez|frozen"
```

`7 passing`을 확인한 뒤 테스트 파일에서 `freezes both sender and recipient and supports release`를 찾아보세요. 동결 중 거절되는 거래와 해제 뒤 성공하는 거래를 비교합니다.

검사는 `_update()`에서 수행합니다. 이 함수는 발행·소각·전송으로 잔액을 바꾸기 전에 공통 조건을 확인하는 곳입니다. 이 코드에서 `approve`는 잔액을 바꾸지 않으므로 전체 중단 중에도 실행할 수 있습니다. 한도를 승인하는 것과 실제로 토큰을 이동하는 것은 다릅니다.

**확인 질문:** 한 고객만 제한하려면 전체 중단과 계정 동결 중 무엇을 사용해야 할까요?

## 실습 4 · 자동 검사 결과 확인하기

**목표:** 성공한 거래뿐 아니라 거절되어야 할 거래도 검사합니다.

```bash
npm test
```

완성 코드의 정상 결과는 `33 passing`입니다. 각 테스트는 준비한 조건에서 코드가 예상대로 동작하는지 확인합니다. `rejects`라는 이름은 거래가 거절되어야 하는 상황을 뜻하므로 테스트 통과와 구분해서 읽으세요.

그다음 실행 범위 보고서를 만듭니다.

```bash
npm run coverage
```

실행 후 `lab/coverage/html/index.html` 파일을 브라우저로 엽니다. 현재 터미널의 `lab` 폴더를 기준으로는 `coverage/html/index.html`입니다. 완성 코드에서는 자체 컨트랙트 3개의 Lines(행)·Statements(문장)가 각각 100%입니다. 모든 조건 조합을 검증했다는 뜻은 아닙니다.

**테스트 작성 연습:** `test/DepositToken.ts`에서 테스트 하나를 읽고 다음 세 가지를 적습니다.

1. 준비: 누가 실행하며, 잔액과 거래 자격은 어떤 상태인가요?
2. 실행: 어떤 동작을 한 번 수행하나요?
3. 예상: 성공하면 무엇이 바뀌고, 실패하면 무엇이 그대로여야 하나요?

강사의 안내에 따라 조건을 바꾼 테스트를 작성하고 `npm test`로 확인하세요. 예를 들어 고객 승인 취소 후 소각 요청을 보내면 어떻게 될지 먼저 예상해 봅니다.

## 실습 5 · 코드 교체 후 잔액 확인하기

**목표:** 프로그램 코드를 교체해도 기존 잔액과 설정이 유지되는지 확인합니다.

`contracts/DepositTokenV2.sol`을 엽니다. 기존 기능을 이어받고 버전을 알려주는 함수 하나를 추가한 예제입니다. 이 예제는 UUPS Proxy 방식을 사용합니다. 고객이 사용하는 주소와 데이터를 유지한 채 내부 코드를 교체합니다.

```bash
npx hardhat test mocha --grep "upgrade"
```

`2 passing`을 확인한 뒤 테스트 파일에서 `preserves address, balances, allowance, roles and controls across upgrade`를 찾아 교체 전후 비교값을 읽어보세요. 잔액 외에 어떤 설정을 유지하는지도 확인합니다. 저장소 호환성 검사가 실패하면 검사를 건너뛰지 말고 강사와 원인을 확인하세요.

## 오류가 나면

수정하던 파일을 더 바꾸기 전에 오류 메시지와 실행한 명령부터 확인하세요.

| 화면에 보이는 내용 | 먼저 할 일 |
|---|---|
| `node`, `git`, `npm` 명령을 찾을 수 없음 | 필요한 프로그램을 설치했는지 확인하고 터미널 다시 열기 |
| `package.json`을 찾을 수 없음 | 현재 위치가 저장소의 `lab` 폴더인지 확인 |
| 모듈을 찾을 수 없음 | `lab` 폴더에서 `npm ci` 실행 |
| Node.js 버전 오류 | `node --version` 확인. 강의 검증 버전은 24.19.0 |
| 컴파일러 다운로드 실패 | 인터넷 연결 확인. 여러 명령을 동시에 실행하지 않고 하나씩 재시도 |
| 테스트 결과에 `failing` 표시 | 실패한 테스트 이름과 오류 메시지를 함께 확인 |

테스트 항목이 모두 통과했다면, 이름에 포함된 `rejects`나 예상 오류 이름 자체는 문제가 아닙니다. 코드 실행 중 나오는 구체적인 오류 뜻은 [용어와 코드 설명](README.md#오류-이름-읽기)을 참고하세요.
